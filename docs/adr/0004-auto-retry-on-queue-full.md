# 队列满时按 1 RPM 节奏重试，并把重试窗口拉到分钟级

实测 `POST /v1/videos` 会返回文档未记载的两类失败：`503 {"code":"video_queue_full"}` 与 `429 rate_limit_exceeded`（免费档限流）。两者都不产生费用、都不是参数错误。官方文档没有记载前者，只在 Token Plan 文档里给出可用的数字：免费档视频模型**实际 RPM 为 1**。完整的实测与出处见 `docs/research/2026-10-17-video-queue-full.md`。

因此创建流程改成：**被判定排队/限流后按 30/45/68/101/152/180 秒递增退避、最多 6 次尝试或 15 分钟预算 + 全程可取消**。节流只作为"被拒之后的冷却"，而不是每次提交的固定节奏。

**Considered Options**

- **重试 2 次、间隔 30 秒**（v1 的做法）：实测等待 15/30/60/120 秒、跨 20 分钟均无法恢复，等于把"必然失败"包装成"试过了"。而且两次重试都落在同一分钟的限流窗口内。
- **无条件按 1 RPM 节流每次提交**：实测证伪——连续生成 5 个视频时第 2~5 个被无谓卡住一分钟，并发用例直接失败。免费档"允许发起 RPM"是 2，正常连发并不必然超限；只有被拒后才需要冷却。
- **无限重试**：队列可能长时间满，无限重试让用户失去控制感，也掩盖真实的不可用。
- **多 Key 自动轮换**：官方文档明确同类型 Key 共享配额池、不会叠加 RPM，单账号轮换无收益；只有同时持有不同类型 Key（免费 / Token Plan）才有意义，属于另一个产品决策，未实现。
- **完全不加退避**：免费档 1 RPM，被拒后立刻再打只会自造 429，掩盖真正的原因。

**Consequences**

- 等待期间必须有明确的"未创建任务、不产生费用"与"取消等待"入口，否则长时间的倒计时会被当成卡死。取消走 `AbortController`，不写历史记录、不弹错误。
- 错误文案不能再承诺"等一分钟通常就能排上"——实测证伪。文案改为说明队列容量由服务端决定，并给出可操作项（继续等 / 取消 / 错开时间）。
- 错误分类必须先按业务码再按状态码：`503` 在文档里是"服务不可用"，在 Agnes 实际是"队列满"，两者的建议动作不同。
- 这两类错误的原始 JSON 形状是顶层 `{code, message, data}`，与文档描述的 `{detail}`、`{error:{message}}` 都不同，`extractRaw` 必须同时兼容三种。
- 轮询侧的 502/503/504 仍走指数退避而非终止（与创建侧策略独立）。
